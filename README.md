# Trauma Team

**Astronaut health monitoring with wearable data, visual symptom reporting, and a roadmap toward evidence-based, mission-aware assistance.**

Trauma Team is a project for the **NASA International Space Apps Challenge 2026**, developed for [Create Health Monitoring Software for Astronauts on Space Missions](https://www.spaceappschallenge.org/2026/challenges/health-monitoring-software/). It brings physiological measurements, daily health check-ins, body observations, and mission activities into one astronaut-facing application.

The project aims to help astronauts understand changes in their health, record discomfort with less effort, and decide when a situation needs attention. Its planned AI assistance will consider where the astronaut is operating and retrieve supporting information from curated resources.

**Development status:** an integrated prototype under active development. Wearable ingestion, mobile monitoring, and persistence for body observations and daily questionnaires are implemented in source. AI, retrieval-augmented generation (RAG), connected scales, and voice commands are planned. This document describes the repository as reviewed on **November 13, 2026**; implementation status does not imply deployment or clinical validation.

## Challenge and project context

The NASA challenge focuses on helping astronauts collect health indicators, evaluate their condition, and act on changes during space missions. Its overview identifies altered gravity, radiation, isolation, confinement, and the spacecraft environment as challenges to astronaut health. [Source: official challenge overview](https://www.spaceappschallenge.org/2026/challenges/health-monitoring-software/).

Trauma Team responds through four connected capabilities:

- **Observe:** collect available wearable readings and review their history.
- **Report:** record symptoms, mood, daily measurements, and discomfort on an interactive body model.
- **Interpret:** show changes and alerts today, then add assistance grounded in retrieved evidence and mission context.
- **Engage:** make recurring health routines easier to follow through daily missions and progress feedback.

The primary user is the astronaut. The current implementation serves one configured user; support for multiple astronauts and operational medical workflows would require additional design.

## What is already implemented

The following status is based on source code, schemas, and configuration in this repository.

| Capability | Current implementation | Remaining work or limitation |
| --- | --- | --- |
| Wearable collection | Zepp OS mini-app for an Amazfit Active 2; heart rate, stress, SpO2, daily steps, and total sleep duration. | Availability depends on readings recorded by the watch, permissions, firmware, and phone connectivity. |
| Background monitoring | Watch App Service, periodic upload cycle, and a watchdog intended to restart an interrupted service. | Recovery depends on Zepp OS execution policies; uninterrupted collection is not guaranteed. |
| Data ingestion | A serverless `POST /api/samples` handler validates readings and stores them in Supabase. Sample identifiers support duplicate handling and daily steps/sleep updates. | Ingestion has no per-device authentication yet. |
| Vital signs dashboard | Mobile cards, measurement history, daily summaries, and backend polling every five seconds. | Polling frequency does not guarantee a new sensor measurement every five seconds. |
| Anatomical reporting | Interactive 3D body model, selectable zones, pain intensity, swelling, functional limitation, and notes. Observations can be saved, loaded, and marked resolved through the backend. | Storage keeps one current record per user and muscle, including its resolved state; it is not a complete history of every change. |
| Daily health questionnaire | Optional glucose, blood pressure, temperature, and sleep inputs, plus mood, symptoms, and notes. One record per user and date can be saved and reloaded. | Status and recommendation text are generated by frontend rules and submitted to the backend. They are not AI output. |
| Alerts | Threshold-based notices for heart rate, stress, SpO2, and questionnaire status, with acknowledgment controls. | Rules are fixed prototype logic, not clinically validated or adapted to mission location. |
| Mission context | Earth, spacecraft/orbital, Moon, and Mars environments; origin, destination, departure and arrival dates; journey progress. | Location is selected or calculated from mission dates, not obtained from navigation hardware. Backend environment persistence is unfinished. |
| Initial gamification | Daily check-ins, a streak display, activity goals, exercise tasks, completion feedback, and a journey timeline. | Mission settings, streaks, and activity completion are held in React state; durable cross-session progression is unfinished. |
| Injury photo follow-up | Camera/gallery selection and a photo sequence viewer associated with body zones. | Photo metadata is held in memory. The upload helper targets an endpoint absent from the backend; durable media upload and retrieval are unfinished. |
| Separate web application | `TraumaTeamWeb/` reserves a place for web work. | It currently contains only a placeholder README. Expo web support and the backend's web-data endpoint do not constitute a separate web application. |

The daily questionnaire can reuse available wearable sleep data. Glucose, blood pressure, and temperature are currently manual inputs, not measurements supplied by the watch integration.

## How the current system connects

```text
Amazfit watch sensors / recorded health data
    -> Zepp OS App Service
    -> BLE / Zepp phone app Side Service network proxy
    -> Watch ingestion API: POST /api/samples
    -> Supabase: samples
    -> NestJS dashboard API
    -> Trauma Team mobile dashboard (five-second polling)

Mobile body observations and daily questionnaires
    -> NestJS dashboard API
    -> Supabase: body_conditions and daily_health_checks
```

The watch ingestion API and the NestJS dashboard API are separate components. The mobile app reads through NestJS rather than querying Supabase directly. NestJS also exposes a Server-Sent Events (SSE) endpoint, although the current mobile hook uses polling.

The main stored records are:

- **`samples`:** metric, value, unit, sample identifier, owner, measurement time, and receipt time. Steps and sleep use daily identifiers for updates.
- **`body_conditions`:** owner, stable muscle identifier, anatomical labels, reported condition, pain, swelling, functional limitation, and active/resolved status.
- **`daily_health_checks`:** owner, date, optional measurements, mood, symptoms, notes, calculated status, and recommendation text.

Measurement and receipt timestamps distinguish when a reading was taken from when it arrived. The current design assigns new watch samples to the server-configured `DASHBOARD_USER_ID` and filters dashboard data for that same user.

## Product roadmap

The following goals capture the team's intended direction. Proposed implementation details and examples remain design choices rather than completed features.

### 1. Assistance that considers the astronaut's location

AI-generated health information must use the astronaut's current operational environment: Earth, spacecraft/transit, a lunar base, or the Martian surface. Mission phase, available equipment, recorded symptoms, and recent readings should accompany that context when available.

The application already changes activity tasks and goals by environment. The next step is to connect reliable, persisted mission context to the assistance workflow. Current environment labels, route durations, exercise targets, and health thresholds are prototype configuration, not validated mission or medical guidance.

**Completion target:** the assistance request includes the current environment and relevant mission context, and the response makes clear how that context affects its interpretation. A selected environment must not be presented as measured location telemetry.

### 2. RAG grounded in challenge and medical resources

Build a retrieval-augmented generation workflow that uses curated challenge resources and relevant space-health references to support interpretation of the pain and symptoms astronauts report. The goal is better-supported diagnostic assistance with traceable evidence; retrieval alone cannot guarantee an accurate diagnosis.

The intended flow is:

```text
Symptoms + body zone + available readings + mission environment
    -> Retrieve relevant passages from a curated resource collection
    -> Generate an explanation grounded in those passages
    -> Return supporting citations, uncertainty, and appropriate next steps
```

Implementation work includes reviewing the challenge resource list, selecting and versioning documents, preparing searchable passages, choosing retrieval and model infrastructure, and evaluating responses against reviewed scenarios. The repository currently contains no RAG corpus, embedding pipeline, vector index, or model integration. No AI provider has been selected in the current code.

**Completion target:** supported statements link to retrieved sources; insufficient evidence is stated explicitly; mission context and reported pain influence retrieval and interpretation. The exact resource collection remains to be curated rather than being implied to exist already.

### 3. Connected scale and automatic body measurements

Integrate a connected scale or compatible body-measurement device to reduce manual entry. Import only values the selected hardware actually provides, retaining units, measurement time, and device provenance. Specific hardware and communication protocols are still to be selected.

The integration must account for the intended gravity environment and distinguish mass from force-based weight readings. Hardware suitability and calibration for each environment remain engineering questions to resolve before using its output in derived indicators.

**Completion target:** a supported device can deliver measurements to the astronaut's record automatically, with visible connection and synchronization status and a manual fallback.

### 4. Voice commands for frequent actions

Add voice shortcuts for actions that currently require tapping through the application. Candidate commands include opening vital signs, starting a daily check-in, navigating to a body zone, and dictating an observation.

Voice interaction should use English commands, provide visible feedback, and let the astronaut review recognized content before saving a health record. Speech recognition technology and offline support are still open decisions.

**Completion target:** selected frequent actions can be completed by voice, with clear recovery from an unrecognized or incorrect command.

### 5. Derived indicators with fewer manual measurements

Research and select documented formulas that can calculate useful additional indicators from measurements already available. The objective is to reduce repetitive entry and show a manageable set of useful results rather than require an overwhelming number of measurements.

Each selected calculation should specify its source, required inputs, units, assumptions, and applicability to the operating environment. Display calculated values as estimates or derived indicators, retain their input provenance, and withhold results when required data is absent or unsuitable. Calculations must not be described as direct sensor measurements.

No medical formula library or agreed set of additional indicators is implemented yet. Existing chart averages and fixed questionnaire thresholds are separate from this planned work.

**Completion target:** each added indicator has a documented calculation and purpose, uses available inputs where appropriate, and communicates missing data and limitations clearly.

### 6. Extend and evaluate gamification

Build on the existing check-ins, streak display, daily tasks, and journey progress. Evaluate which mechanisms help astronauts maintain routines without adding distraction or unnecessary work.

Candidate extensions include persistent progress, milestones, optional reminders, personalized activity goals, and recovery-focused tasks. Goals should accommodate symptoms, rest, and mission constraints. These extensions are proposals to evaluate; they are not all committed features.

**Completion target:** progress survives application restarts, daily completion is handled consistently, and engagement features support appropriate health behavior without rewarding the concealment of symptoms or inappropriate exertion.

## English throughout the project

**English is the required language for the entire system and its documentation.** This includes mobile and watch interfaces, future web screens, alerts, generated assistance, voice commands, developer documentation, code comments, and new project terminology.

This README follows that requirement. The existing repository still contains Spanish interface strings, comments, component documentation, environment identifiers, anatomical categories, and symptom values. Migration to English is therefore an explicit remaining task.

Some Spanish values are part of API validation and database constraints, not just visible labels. Their migration must coordinate frontend code, backend contracts, stored records, and SQL constraints so existing data remains readable. Existing directory names can continue to identify their current paths while this work is planned.

## Suggested implementation sequence

1. **Consolidate the prototype:** migrate language consistently, persist mission and gamification state, finish photo storage, and make failed synchronization recoverable.
2. **Strengthen identity and data quality:** replace the shared-user prototype access model, authenticate ingestion devices, distinguish stale readings from fresh data, and define reliable handling of interrupted connectivity.
3. **Build evidence-backed assistance:** curate resources, implement and evaluate retrieval, and supply persisted mission context to the AI workflow.
4. **Reduce interaction effort:** integrate selected scale hardware, documented derived indicators, and voice shortcuts.
5. **Evaluate the complete experience:** review usability, engagement, data reliability, and the quality of assistance across representative mission scenarios.

This sequence is a proposed dependency order, not a delivery schedule.

## Running the existing prototype

Use **Node.js 20 or later** for the backend, a configured Supabase project, and separate terminals for the backend and mobile app. Watch development additionally requires Zepp/Zeus tooling and compatible hardware paired with the Zepp phone app.

### Database and service configuration

Create the base sample table with [`Wachimoles_Reloj/supabase/schema.sql`](./Wachimoles_Reloj/supabase/schema.sql). For an existing database, review the [watch migrations](./Wachimoles_Reloj/supabase/migrations/) and [backend migrations](./Wachimoles_Backend/supabase/migrations/) for daily steps, user ownership, body conditions, daily questionnaires, and sleep support.

Create `Wachimoles_Backend/.env` with your own values:

```dotenv
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_SERVICE_ROLE_KEY=your-server-only-service-role-key
DASHBOARD_USER_ID=your-supabase-user-uuid
DASHBOARD_API_TOKEN=your-random-token-at-least-32-characters
DASHBOARD_WEB_PASSWORD=your-separate-password-at-least-16-characters
CORS_ORIGINS=http://localhost:8081
PORT=3000
```

Set `CORS_ORIGINS` to the browser origins actually used if running a web client. Native requests may omit the `Origin` header.

```powershell
cd Wachimoles_Backend
npm ci
npm run start:dev
```

Create `TraumaTeamMovil/.env`:

```dotenv
EXPO_PUBLIC_API_BASE_URL=http://your-computer-lan-address:3000
EXPO_PUBLIC_DASHBOARD_API_TOKEN=the-same-prototype-dashboard-token
```

Use an address reachable from the device or emulator. The mobile data client permits HTTP in development and requires HTTPS outside development.

```powershell
cd TraumaTeamMovil
npm ci
npm start
```

For watch ingestion, configure `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and the same `DASHBOARD_USER_ID` in the watch API's server environment. Set `SAMPLE_API_URL` in [`app-side/config.js`](./Wachimoles_Reloj/app-side/config.js) to that API's endpoint, then build and install the watch app. The [watch README](./Wachimoles_Reloj/README.md) contains the existing hardware workflow; it still needs English translation and correction of legacy paths. The optional local JSON Lines server is a development path and does not automatically feed the Supabase-backed mobile dashboard.

Keep real `.env` files out of version control; not every component currently supplies a tracked `.env.example`.

## Prototype boundaries

Trauma Team is a hackathon prototype. Its consumer-wearable readings, fixed health rules, and planned AI assistance have not been validated for diagnosis or mission-critical use.

Current technical constraints relevant to the roadmap include:

- The mobile app embeds a shared dashboard token through `EXPO_PUBLIC_*` configuration. Such values can be extracted from the client; the current access model must be replaced before broader distribution.
- Supabase service-role credentials belong only on the server. Because that role bypasses Row Level Security, explicit backend ownership filters remain essential.
- The watch upload endpoint validates sample structure but does not establish individual device identity.
- There is no durable offline upload queue. Phone connectivity and OS interruptions can leave gaps; the 3D viewer also loads rendering dependencies from external CDNs.
- Existing component READMEs contain legacy names and paths. Use the actual repository layout and source-linked references here when resolving discrepancies.
